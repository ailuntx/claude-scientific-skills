# 拉取请求文档模板

> **返回 [Markdown 风格指南](../markdown_style_guide.md)** — 请先阅读风格指南了解格式、引用和表情符号规则。

**使用场景：** 将拉取请求记录为持久化、可搜索的 Markdown 文档。此文件即 PR 本身——而非附属文档。它完整记录变更内容、原因、验证方式、安全影响、部署策略及经验总结。

**核心功能：** 含影响分类的摘要、变更清单（含前后对比）、测试证据、安全审查、破坏性变更文档、部署策略、可观测性方案、回滚计划及审查者清单。

**理念：** 此文件即 PR 描述——不是附属品、补充物或副本。GitHub PR 仅作为轻量指针：人类在此查看差异、批准并关注 CI。但实际记录——变更内容、原因、测试证据、回滚计划及经验总结——存于此处，随仓库提交。

当六个月后有人问"PR #123 是什么？"时，他们应 `grep docs/project/pr/` 而非查询 GitHub API。当从 GitHub 迁移至 GitLab 时，所有 PR 记录随迁。当 AI 代理需理解模块历史时，它直接读取本地文件——无令牌消耗、无速率限制、无平台依赖。

这遵循[万物皆代码](../markdown_style_guide.md#-everything-is-code)理念：项目管理数据存于仓库中，具备版本控制与可移植性。勿将应存于此文件的信息留在 GitHub 界面。投入十分钟，优秀的 PR 文件能消除"这个 PR 是什么？"的 Slack 消息和"谁能查下 GitHub PR？"的上下文切换——答案已在仓库中。

## 文件规范

```
docs/project/pr/pr-00000123-fix-auth-timeout.md
docs/project/pr/pr-00000124-add-job-retry-metrics.md
docs/project/pr/pr-00000125-refactor-ci-stage-order.md
```

- **目录：** `docs/project/pr/`
- **命名：** `pr-` + 8位零填充PR编号 + `-` + 简短小写连字符描述
- **交叉引用：** 在元数据表中链接至实际 PR
- **GitHub PR 正文：** 仅使用此文件的分支完整 URL（例如 `https://github.com/<org>/<repo>/blob/<branch>/docs/project/pr/pr-00000123-fix-auth-timeout.md`）
