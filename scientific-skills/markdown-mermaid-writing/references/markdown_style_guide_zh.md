# Markdown 风格指南

> **面向 AI 代理：** 阅读本文档以了解所有核心格式规则。创建任何 Markdown 文档时，请遵循这些约定以确保输出一致且专业。若存在对应文档类型的模板，请基于模板开始创作——参见[模板](#模板)。
>
> **面向人类：** 本指南确保项目中每个 Markdown 文档都保持简洁、可快速浏览、引用规范，并在 GitHub 上完美渲染。请将其引用至你的 `AGENTS.md` 或贡献指南中。

**目标平台：** GitHub Markdown（议题、拉取请求、讨论、Wiki、`.md` 文件）  
**设计目标：** 通过一致的结构、有意义的格式、规范引用和策略性图表运用，创建清晰专业的有效沟通文档。

---

## 代理快速入门

1. **识别文档类型** → 检查是否存在[模板](#模板)
2. **结构优先** → 先构建标题层级，再填充内容
3. **应用本指南格式** → 标题、文本、列表、表格、图像、链接
4. **添加引用** → 所有主张和来源均需脚注标注
5. **考虑图表** → 是否用 [Mermaid 图表](mermaid_style_guide.md)比文字表达更有效？
6. **添加可折叠区块** → 用于补充细节、演讲备注或冗长背景
7. **验证** → 执行[质量检查清单](#质量检查清单)

## 核心原则

| #   | 原则                         | 规则                                                                                                                                                                                       |
| --- | ---------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 1   | **先于疑问解答**             | 预判读者问题并内联解答。优秀文档应在疑问形成时即时消解——读者读完不会遗留"但要是..."的困惑                                                                                                |
| 2   | **优先可浏览性**             | 读者先浏览后细读。运用标题、粗体和列表实现结构一目了然                                                                                                                                     |
| 3   | **引用一切**                 | 每个主张、数据或外部参考均需带完整 URL 的脚注引用。杜绝无源声明                                                                                                                           |
| 4   | **图表优于文字墙**           | 涉及流程、关系或结构的概念，应在文字旁使用 [Mermaid 图表](mermaid_style_guide.md)                                                                                                         |
| 5   | **信息充分呈现**             | 勿隐藏细节——主动展示。使用可折叠区块承载深度内容而不显杂乱，但绝不因"他们可能不需要"而省略信息。相关即包含                                                                               |
| 6   | **结构一致性**               | 所有文档保持相同标题层级、相同格式模式、相同表情符号位置                                                                                                                                   |
| 7   | **每节一主题**               | 每个标题应聚焦单一主题。若涉及两个观点，请拆分为两个标题                                                                                                                                   |
| 8   | **专业而不失亲和**           | 格式简洁、无冗余、无装饰性噪音——但避免刻板或学术化。以高级工程师向同事讲解的方式书写                                                                                                     |

## 🗂️ 万物皆代码

万物皆代码。拉取请求、议题、看板——它们都是仓库中的 Markdown 文件，而非困在平台数据库中的数据。

### 重要性

- **可移植** — GitHub → GitLab → Gitea → 任意平台。项目管理数据不锁定于任何供应商。切换平台时议题、PR 记录和看板随行——它们只是文件
- **AI 原生** — 代理可通过本地文件访问读取每个议题、PR 记录和看板。无需 API 令牌、无速率限制、无平台特定查询。`grep` 永远优于 `gh api`
- **可审计** — 项目管理变更与代码变更遵循相同 PR 审查流程。每次看板更新、每次议题状态变更——均存于 git 历史记录并附时间戳和归属

### 实现方式

| 内容                 | 存储位置                                              | GitHub 角色                                                                                                                                               |
| -------------------- | ----------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **拉取请求**         | `docs/project/pr/pr-NNNNNNNN-short-description.md`    | GitHub PR 是轻量指针——人类在此评论差异、批准和观察 CI。变更内容、原因及经验总结存于文件                                                                   |
| **议题**             | `docs/project/issues/issue-NNNNNNNN-short-description.md` | GitHub Issues 是通知评论层。错误报告、功能请求、调查日志和解决方案存于文件                                                                                |
| **看板**             | `docs/project/kanban/{scope}-{id}-short-description.md` | 无需外部看板工具。在分支中修改看板，随 PR 合并。看板随代码库演进                                                                                          |
| **决策记录**         | `docs/decisions/NNN-{slug}.md`                        | 完全脱离 GitHub——纯仓库原生                                                                                                                               |

### 核心规则

> 📌 **勿将应存于文件的信息捕获在 GitHub UI 中。** 在 GitHub 批准 PR。在 GitHub 观察 CI。在 GitHub 评论。但实质内容——描述、调查、决策——存于提交的文件中。若值得书写，便值得提交。

### 跟踪文档模板

- [拉取请求记录](markdown_templates/pull_request.md) — PR 描述即此文件
- [议题记录](markdown_templates/issue.md) — 作为仓库文件的错误报告和功能请求
- [看板](markdown_templates/kanban.md) — 随代码合并的迭代/项目看板

目录结构与命名参见[文件约定](#跟踪文档的文件约定)

## 文档结构

### 标题与元数据

每份文档以唯一 H1 标题开头，后接简要上下文行和分隔符：

```markdown
# 文档标题

_单行简要上下文——项目名、日期或目的_

---
```

- **每文档仅一个 H1** — 绝不多于一个
- 斜体上下文行——说明文档性质、时间及受众
- 水平分隔线隔离元数据与内容

### 标题层级

| 层级 | 语法            | 用途                     | 单文档上限      |
| ---- | --------------- | ------------------------ | --------------- |
| H1   | `# 标题`        | 文档标题                 | **1**（仅一个） |
| H2   | `## 章节`       | 主要章节                 | 4–10            |
| H3   | `### 主题`      | 章节内主题               | 每 H2 下 2–5    |
| H4   | `#### 子主题`   | 必要时细分主题           | 每 H3 下 2–4    |
| H5+  | 禁用            | —                        | 0               |

**规则：**

- **禁止跨级跳跃** — 勿从 H2 直接跳至 H4
- **H2 标题添加表情符号** — 每个 H2 起始处放一个：`## 📋 项目概览`
- **H3/H4 禁用表情符号** — 保持子标题简洁
- **句子首字母小写** — `## 📋 项目概览` 而非 `## 📋 项目概览`（专有名词除外）
- **描述性标题** — `### 认证流程` 而非 `### 详情`

## 文本格式

### 粗体、斜体、代码

| 格式       | 语法         | 使用场景                                   | 示例                             |
| ---------- | ------------ | ------------------------------------------ | -------------------------------- |
| **粗体**   | `**文本**`   | 关键术语、重要概念、强调                   | **主数据库**处理写入             |
| _斜体_     | `*文本*`     | 定义、标题、弱强调                         | 该流程称为 _分片_                |
| `代码`     | `` `文本` `` | 技术术语、命令、文件名、值                 | 运行 `npm install` 安装          |
| ~~删除线~~ | `~~文本~~`   | 废弃内容、修正                             | ~~旧方案~~已被 v2 替代           |

**规则：**

- **慎用粗体** — 处处粗体则无重点。每段落最多 2–3 个粗体术语
- **禁止组合格式** — 勿同时使用粗斜体（`***文本***`）
- **技术内容用代码格式** — 文件名（`README.md`）、命令（`git push`）、配置值（`true`）、环境变量（`NODE_ENV`）
- **禁用整句粗体** — 仅加粗句内关键词

### 引用块

用于定义、提示和重要说明：

```markdown
> **定义：** _负载均衡器_ 将传入网络流量
> 分发至多台服务器，确保单台服务器不过载。
```

警告和提示：

```markdown
> ⚠️ **警告：** 此操作不可逆且具破坏性。

> 💡 **技巧：** 使用 `--dry-run` 预览变更再应用。

> 📌 **注意：** 此操作需仓库管理员权限。
```

- 使用表情符号+粗体标签分类提示
- 引用块保持 1–3 行
- 禁止嵌套引用块（`>>`）

## 列表

### 列表类型适用场景

| 类型     | 语法       | 适用场景                     |
| -------- | ---------- | ---------------------------- |
| 无序列表 | `- 项`     | 项目无固有顺序               |
| 有序列表 | `1. 步骤`  | 需按顺序执行的步骤           |
| 复选框   | `- [ ] 项` | 跟踪完成情况（议程、检查表） |

### 格式规则

- **缩进一致** — 子项缩进 2 空格（部分渲染器用 4 空格；选定即坚持）
- **平行结构** — 同列表项语法结构一致
- **非完整句结尾不加句号**
- **项内容简洁** — 若需段落说明，应转为子章节
- **最大嵌套深度：2 层** — 需第三层时请重组结构

```markdown
✅ 良好——平行结构，简洁：

- 配置数据库连接
- 运行迁移脚本
- 验证模式变更

❌ 不佳——结构混杂，冗长：

- 你需要配置数据库
- 迁移脚本
- 之后应验证模式是否正确
```

## 链接与引用

### 内联链接

```markdown
图表规范参见 [Mermaid 风格指南](mermaid_style_guide.md)。
```

- **链接文本有意义** — `[Mermaid 风格指南]` 而非 `[点击这里]` 或 `[链接]`
- **内部链接用相对路径** — `[指南](./README.md)` 而非绝对 URL
- **外部链接用完整 URL** — 始终 `https://`

### 脚注引用

**每个主张、数据或外部参考必须附带脚注引用。** 这是可信度的硬性要求。

```markdown
Markdown 由 John Gruber 于 2004 年创建，是一种
为可读性设计的轻量级标记语言[^1]。GitHub 于
2022 年 2 月支持 Mermaid 图表[^2]。

[^1]: Gruber, J. (2004). "Markdown." _Daring Fireball_. https://daringfireball.net/projects/markdown/

[^2]: GitHub 博客. (2022). "使用 Mermaid 在 Markdown 文件中嵌入图表." https://github.blog/2022-02-14-include-diagrams-markdown-files-mermaid/
```

**引用格式：**

```
[^N]: 作者/机构. (年份). "标题." *出版物*. https://完整链接
```

**规则：**

- **顺序编号** — 按出现顺序使用 `[^1]`, `[^2]`, `[^3]`
- **必须包含完整 URL** — 确保读者可访问来源
- **脚注集中置于文档底部** — 放在 `## 参考文献` 章节或文档末尾
- **每个外部主张均需引用** — 数据、引用、方法论、提及的工具
- **内部项目链接无需脚注** — 改用内联链接

### 引用式链接（重复 URL 时）

当同一 URL 多次出现时，使用引用式链接保持文本整洁：

```markdown
[官方文档][mermaid-docs] 涵盖所有图表类型。
完整语法参见 [Mermaid 文档][mermaid-docs]。

[mermaid-docs]: https://mermaid.js.org/ 'Mermaid 文档'
```

## 图像与图示

### 放置位置与语法

```markdown
![屏幕阅读器描述文本](images/architecture_overview.png)
_图 1：展示三层部署模型的系统架构_
```

**规则：**

- **与相关内容内联** — 图像置于关联位置，勿单独放"图像"章节
- **描述性替代文本** — `![三层架构图]` 而非 `![图片]` 或 `![截图]`
- **下方斜体标注** — `*图 N：图示说明*`
- **图示顺序编号** — 多图时使用图 1、图 2 等
- **相对路径** — `images/文件.png` 而非绝对路径
- **合理文件大小** — 压缩 PNG，优先 SVG

### 图像命名规范

```
{文档缩写}_{描述}.{扩展名}

示例：
  auth_flow_overview.png
  deployment_architecture.svg
  api_response_example.png
```

### 何时避免使用图像

若内容可表达为 **Mermaid 图表**，优先选用而非静态图：

| 场景                   | 推荐方案                                  |
| ---------------------- | ----------------------------------------- |
| 架构图                 | Mermaid `flowchart` 或 `architecture-beta` |
| 序列/交互图            | Mermaid `sequenceDiagram`                 |
| 数据模型               | Mermaid `erDiagram`                       |
| 时间轴                 | Mermaid `timeline` 或 `gantt`             |
| UI 截图                | 图像（Mermaid 无法实现）                  |
| 真实场景照片           | 图像                                      |
| 复杂数据可视化         | 图像或 Mermaid `xychart-beta`             |

图表类型选择与样式参见 [Mermaid 风格指南](mermaid_style_guide.md)

## 表格

### 适用场景

- **结构化对比** — 功能、选项、权衡
- **参考数据** — 配置值、API 参数、状态码
- **计划与矩阵** — 时间线、责任分配

### 禁用场景

- **叙述性内容** — 改用段落
- **简单列表** — 改用项目符号
- **超 5 列** — 移动端难阅读；需重组

### 格式规范

```markdown
| 功能     | 免费版 | 专业版 | 企业版     |
| -------- | ------ | ------ | ---------- |
| 用户数   | 5      | 50     | 无限制     |
| 存储空间 | 1 GB   | 100 GB | 自定义     |
| 支持服务 | 社区   | 邮件   | 专属支持   |
```

**规则：**

- **必须含标题行** — 禁用无标题表格
- **文本列左对齐** — `|---|`（默认）
- **数字列右对齐** — 适用时用 `|---:|`
- **单元格内容简洁** — 每格 1–5 词。若需更多，则不适合表格
- **关键列加粗** — 首列或读者优先扫描列
- **列内格式一致** — 勿混用句子与片段

## 代码区块

### 行内代码

在行文中的技术术语使用反引号：

```markdown
运行 `git status` 检查未提交变更。
`NODE_ENV` 变量控制运行时环境。
```

### 围栏代码块

始终指定语言以实现语法高亮：

````markdown
```python
def calculate_average(values: list[float]) -> float:
    """计算列表数值的算术平均值"""
    return sum(values) / len(values)
```
````

**规则：**

- **必须含语言标识符** — ` ```python `, ` ```bash `, ` ```json ` 等
- **纯文本输出用 ` ```text `** — 禁用无语言标识的 ` ``` `
- **保持区块聚焦** — 仅展示相关片段而非完整文件
- **需上下文时添加注释** — 区块顶部加 `# 配置数据库连接`

## 可折叠区块

使用 HTML `<details>` 承载不应干扰主流程的补充内容——演讲备注、实现细节、冗长日志或深度解读。

```markdown
<details>
<summary><strong>💬 演讲备注</strong></summary>

- 核心要点一
- 过渡至下一主题
- **粗体**强调在区块内有效
- [链接](https://example.com)同样适用

</details>

---
```

**规则：**

- **默认折叠** — `<details>` 标签自动折叠
- **描述性摘要** —

- **内部支持任何Markdown格式** — 项目符号、粗体、链接、代码块、表格

### 常见的可折叠模式

| 摘要标签              | 用途                                             |
| --------------------- | ------------------------------------------------ |
| 💬 **演讲者笔记**     | 演示要点、时间安排、过渡                         |
| 📋 **详情**           | 扩展解释、详细上下文                             |
| 🔧 **实现**           | 技术细节、代码示例、配置                         |
| 📊 **原始数据**       | 完整输出、日志、数据表                           |
| 💡 **背景**           | 有帮助但非必需的上下文                           |

## 水平分隔线

使用 `---`（三个连字符）进行视觉分隔：

```markdown
---
```

**使用场景：**

- **在每个 `</details>` 块之后** — 强制要求，创建清晰分隔
- **标题/元数据之后** — 分隔文档头部与内容
- **主要章节之间** — 当仅用H2标题不足以形成视觉间隔时
- **脚注/参考文献之前** — 分隔内容与引用列表

**避免场景：**

- 段落之间（过于密集）
- 同一H2章节内的H3子章节之间（改用空白行）

## 批准的Emoji集合

每个H2标题开头使用一个emoji。正文中仅限关键标注和强调时谨慎使用。

### 章节标题

| Emoji | 用途                               |
| ----- | ---------------------------------- |
| 📋    | 概述、摘要、议程、清单             |
| 🎯    | 目标、成果、指标                   |
| 📚    | 内容、文档、主体部分               |
| 🔗    | 资源、参考文献、链接               |
| 📍    | 议程、导航、当前位置               |
| 🏠    | 事务安排、后勤、通知               |
| ✍️    | 任务、作业、行动项                 |

### 状态与结果

| Emoji | 含义                               |
| ----- | ---------------------------------- |
| ✅    | 成功、完成、正确、已批准           |
| ❌    | 失败、错误、避免、已拒绝           |
| ⚠️    | 警告、注意、重要通知               |
| 💡    | 技巧、洞察、想法、最佳实践         |
| 📌    | 重要、关键点、需记住               |
| 🚫    | 禁止、不可操作、已阻止             |

### 技术与流程

| Emoji | 含义                           |
| ----- | ------------------------------ |
| ⚙️    | 配置、设置、流程               |
| 🔧    | 工具、实用程序、设置           |
| 🔍    | 分析、调查、评审               |
| 📊    | 数据、指标、分析               |
| 📈    | 增长、趋势、改进               |
| 🔄    | 循环、刷新、迭代               |
| ⚡    | 性能、速度、快速操作           |
| 🔐    | 安全、认证、隐私               |
| 🌐    | 网络、API、全局                |
| 💾    | 存储、数据库、持久化           |
| 📦    | 包、制品、部署                 |

### 人员与协作

| Emoji | 含义                             |
| ----- | -------------------------------- |
| 👤    | 用户、个人、个体                 |
| 👥    | 团队、小组、协作                 |
| 💬    | 讨论、评论、演讲者笔记           |
| 🎓    | 学习、教育、知识                 |
| 🤔    | 问题、思考、反思                 |

### Emoji规则

1. **每个H2标题开头仅一个** — `## 📋 概述`
2. **H3/H4禁止使用** — 保持子标题简洁
3. **正文中谨慎使用** — 仅用于标注（`> ⚠️ **警告：**`）和关键标记
4. **禁止位置**：主标题（H1）、代码块、链接文本、表格数据单元格
5. **禁用装饰性emoji** — 🎉 💯 🔥 🎊 💥 ✨ 增加噪音而非意义
6. **一致性** — 相同emoji在全项目文档中代表相同含义

### 集成方式

将图表**与相关文本内联放置**，勿单独成节：

````markdown
### 认证流程

登录流程验证凭证、检查MFA状态并签发会话令牌。失败尝试会记录用于安全监控。

‎```mermaid
sequenceDiagram
accTitle: 登录认证流程
accDescr: 用户通过API和认证服务的登录顺序

    participant U as 👤 用户
    participant A as 🌐 API
    participant S as 🔐 认证服务

    U->>A: POST /login
    A->>S: 验证凭证
    S-->>A: ✅ 签发令牌
    A-->>U: 200 OK + 会话

‎```

令牌24小时后过期。刷新令牌细节参见[认证流程](#认证流程)。
````

**始终遵循[Mermaid样式指南](mermaid_style_guide.md)** 设置图表样式——emoji、颜色类、无障碍性（`accTitle`/`accDescr`）及类型特定规范。

## 空白与间距

- **段落间空行** — 始终
- **标题前后空行** — 始终
- **代码块前后空行** — 始终
- **引用块前后空行** — 始终
- **列表项间无空行** — 保持列表紧凑
- **无行尾空格** — 清洁行尾
- **文件末尾保留一个空行** — 标准规范
- **连续空行不超过一行** — 两行空
